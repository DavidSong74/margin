## 2024-08-24 - Privilege Escalation in SECURITY DEFINER & Improper Email Masking Exposure
**Vulnerability:** Privilege escalation (search path hijacking) in `find_user_by_email` and `get_comments` due to `SET search_path = public, auth`, and inadvertent data exposure due to faulty email masking logic (`regexp_replace`) concatenating the unreplaced domain duplicate.
**Learning:** `SECURITY DEFINER` functions must strictly bind their execution context to `SET search_path = ''` to prevent malicious schema overriding. In addition, regex replacements that only target specific sections (e.g. prefix) will leave trailing portions unmodified; subsequent string concatenation using standard indexing must account for this to prevent duplicating sensitive data pieces (like domain names).
**Prevention:** Always use `SET search_path = ''` combined with fully qualified names (e.g., `pg_catalog.lower`, `public.feed_comments`) for functions bypassing RLS. Use absolute substring operations (`pg_catalog.left`, `pg_catalog.split_part`) for structural string masking instead of regex replacement when masking structured values like emails.
